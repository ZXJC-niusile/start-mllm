# 05 Embedding 与 Tokenizer

前置：[04 神经网络与学习过程](./04-神经网络与学习过程.md)。本章连接文本编码、向量表示和下一 token 预测，建立阅读语言模型的输入输出基础。

模型不直接对 Python 字符串做矩阵乘法。文本先按 tokenizer 的规则编码为离散 ID，再从 embedding 参数表取出向量，网络才开始处理连续表示。Tokenizer、embedding 与语言模型各有职责，不能都简称为“把文字变成向量”。

## 5.1 字符、词和 token 不是同一种单位

字符是文字编码中的基本组成，日常所说的词依赖语言习惯，token 则由具体分词规则决定。一个英文单词可能被拆成多个子词，一个汉字也未必恰好对应一个 token；标点、空格、换行可能影响切分。准确长度需要使用配套 tokenizer 计算，不能按字符数固定换算。

词表（vocabulary）登记可用 token 与 ID 的对应关系。一个人为定义的例子是：`我→0`、`爱→1`、`猫→2`、`<eos>→3`，于是“我 爱 猫”按本例的空格规则编码成 `[0,1,2]`。这是解释流程的玩具词表，不是某个真实模型的切分结果。

ID 只是地址。把“猫”编号为 2 不表示它比编号 1 的“爱”多一个语义单位，也不能用 ID 差值判断相似度。模型 checkpoint、词表和特殊 token 配置应配套使用；不同模型的同一个 ID 可能代表完全不同的片段。

## 5.2 子词与字节怎样处理未见词

若每个完整词都占一个词表位置，生僻词、新术语和拼写变化会不断扩大词表；若只用很小的字符或字节单位，序列又可能很长。子词方法在两者之间折中。

BPE 的基本思路是从小单位开始，根据语料统计逐步合并常见相邻片段；编码时按照已学到的合并规则工作，不是临时按词义拆分。其他方法如 WordPiece、Unigram 使用不同的词表构建与分解规则。字节级表示或字节回退可以改善罕见字符的覆盖，但不能据此保证所有 tokenizer 都不产生未知标记。

Tokenizer 还可能有文本规范化和预切分步骤，所以“编码再解码”是否逐字符还原，取决于配置。它处理的是表示规则，不是在执行语言理解。[Hugging Face Tokenizers 概念说明](https://huggingface.co/docs/tokenizers/en/components)将这些环节分开介绍。

## 5.3 Embedding：用 ID 取出一行可学习参数

设词表大小为 `V=4`，向量宽度为 `D=2`，人工设定嵌入表：

```text
E = [[1,0], [0,1], [1,1], [0,0]]     形状 [V,D]=[4,2]
IDs = [0,1,2]                         形状 [T]=[3]
E[IDs] = [[1,0], [0,1], [1,1]]        形状 [T,D]=[3,2]
```

这一步是查表，不是把 ID 乘一个系数。批量输入 `[B,T]` 会变成 `[B,T,D]`，其中 `T` 是序列长度，`D` 是每个位置的特征宽度。把词表扩展一行，与把序列增加一个位置，是两种完全不同的变化。

Embedding 表是模型参数，训练会调整相关向量。查表得到的是某 token 的初始表示；经过上下文网络后，同一 token 在不同句子中的表示可以不同。“苹果”在水果描述和品牌讨论中可以得到不同的上下文特征，不能只拿初始表的一行当作最终词义。

## 5.4 相似度为什么需要先说明表示来源

两个向量可以用点积、距离或余弦相似度比较。余弦相似度是点积除以两个向量的长度；非零向量归一化后，点积就等于余弦。零向量没有可直接定义的方向，需要明确处理约定。

但“能计算相似度”不等于“这个表示适合检索”。输入 embedding、某层隐藏状态、经过池化的句向量和经过对比学习的表示，具有不同用途。若没有相应训练目标，直接平均所有 token 向量未必能得到可靠的句子检索表示。后面的 CLIP 会专门解释怎样用学习目标让图文相似度有用。

## 5.5 Padding、mask 与上下文长度

同一 batch 的文本长度可能不同，例如两条长度分别为 3 和 5。为了形成规则数组，可以把短序列补齐到 5，形成 `[B,T]`。这些补齐位置不是用户实际输入，需要用有效位置标记告诉相关计算哪些位置应忽略。

padding mask 处理补齐位置，causal mask 处理当前位置是否能看未来，它们解决不同问题。损失中忽略标签的设置又是另一层控制：某位置不参与损失，不等于这个位置一定不能作为上下文被读取。具体接口里布尔 mask 的真值含义和形状也可能不同，要按函数定义解释。

上下文预算既要容纳提示，也要考虑生成的回答；多模态模型还可能把一张图展开成许多视觉位置。仅看到用户打了十几个字，不能断言输入很短。不同模型的图像压缩、位置规则和预算限制不同，需要查看配套 processor 与配置。

## 5.6 对话角色怎样进入一条序列

`system`、`user`、`assistant` 是结构化消息中的角色。模型实际接收的通常仍是一条带分隔标记的 token 序列。chat template 负责把角色、内容、消息边界以及需要的生成起始标记组织成模型熟悉的格式。

因此手工把所有消息正文拼成字符串，可能丢失谁在说话和在哪里开始回答的信息。不同模型模板不能任意互换。某些模板已经加入特殊 token；后续编码若又自动添加一遍，就可能重复。`add_generation_prompt` 这类选项用于某些模板的回答开头安排，不表示添加了标准答案。相关行为见 [Transformers chat template 文档](https://huggingface.co/docs/transformers/main/en/chat_templating)。

对图文消息，processor 往往同时协调文本模板、图像预处理和图像占位信息。一个图像标记也可能对应多个实际视觉 token，不能把字符串中的一个占位符当作只占一个序列位置。

## 5.7 输出词表与下一 token

网络为每个文本位置产生隐藏表示 `[B,T,D]`，输出头把它变成词表分数 `[B,T,V]`。其中每个位置的 `V` 个 logits 表示下一 token 的候选分数；输入端的查表和输出端的词表投影不是同一步，有些模型共享相关权重，有些不共享。

例如序列“我 爱 猫 `<eos>`”，训练时可用前缀“我”预测“爱”，用“我 爱”预测“猫”，再预测结束标记。标签与输入位置错开一位。生成时没有后续真实答案可用，而是把新选出的 token 接回输入，继续预测；遇到结束条件或长度上限就停止。

Tokenizer 只负责把最终 ID 还原成文本片段，不负责判断答案对错。下一章解释：这些向量如何通过注意力读取上下文，得到用于下一 token 预测的表示。

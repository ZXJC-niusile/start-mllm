# 09 多模态大模型入口：Vision Encoder + Connector + LLM

前置：[08 CLIP 与图文对齐](./08-CLIP与图文对齐.md)。本章沿一次图文问答连接视觉编码器、连接器与语言模型，再说明它们如何进入正文的架构、训练与评测讨论。

## 9.1 从“收到一张图片”开始追踪

用户发送图片和问题，应用把它们组织成消息；processor 根据模型约定处理图像与文字；视觉编码器提取图像特征；连接器把特征变成语言模型可读取的表示；语言模型结合问题生成文本。

以“票据总金额是多少”为例，每一步的产物都不同：

| 环节 | 主要输入 | 主要输出 | 需要理解的边界 |
| --- | --- | --- | --- |
| 消息与模板 | 图片、问题、角色 | 模型约定的消息结构与序列安排 | 角色和图像位置不能随意拼接 |
| 图像预处理 | 原始图片 | 像素张量及尺寸等信息 | 裁剪或缩放可能丢失金额文字 |
| 视觉编码器 | 像素张量 | 一组视觉特征 | 特征不是已经核验的 OCR 答案 |
| 连接器 | 视觉特征 | 适配后的视觉表示 | 维度一致不证明语义可用 |
| 语言模型 | 视觉条件、问题与已生成前缀 | 下一文本 token 的分数 | 答案需要与图像证据核对 |
| 解码与应用 | 输出 token ID | 文本或解析后的字段 | 格式正确仍可能金额错误 |

## 9.2 用一组形状连接三个模块

下面选用人工缩小的数字，只为解释接口。假设一张图被视觉编码器表示为 16 个 token，每个宽度为 8：

```text
视觉特征 F：[B,16,8]
线性连接器 W：[8,12]
投影后 Z = F W：[B,16,12]
文本 embedding E：[B,T,12]
```

在一种简化的视觉前缀方案中，Z 与文本 embedding 按模型规则排列到同一序列，长度约为 `16+T`，宽度仍为 12。实际还可能有图像边界、角色、位置和其他特殊标记，不能把这个简式当作任意模型的精确长度公式。

这里 W 对每个视觉 token 分别处理，只改变特征宽度。它不会自动把 16 个 token 压成 4 个，也没有让一个 token 读取另一个 token。若连接器是多层 MLP，可以增加非线性转换；若它含重采样或池化，还可能改变 token 数，必须重新追踪形状。

## 9.3 接入同一序列与交叉注意力

一种方案把适配后的视觉向量放进语言输入序列，语言 decoder 通过自己的注意力读取它们。早期 [LLaVA](https://arxiv.org/abs/2304.08485)提供了连接视觉编码器与语言模型、再做视觉指令学习的代表性思路；不能把其具体配置概括为所有 MLLM 的固定配方。

另一种方案让视觉表示保留为独立记忆，由 cross-attention 读取：文本位置生成 Q，视觉位置生成 K/V。若文本长度 T、视觉长度 N，交互分数为 `[T,N]`。它与把所有位置直接拼成一条序列不同，但都需要训练出有用的跨模态读取方式。

可学习查询、resampler 等模块还能用较少输出位置读取较多输入位置。压缩减小后续处理成本，同时形成信息瓶颈；小字、计数与复杂布局是否被保留，需要任务评测。更多连接方式见[第三章](../chapter3/第三章%20多模态生成架构.md)。

## 9.4 “形状接上”之后为什么还需要学习

随机 W 也能把宽度从 8 变为 12，但输出分量未必符合语言模型使用输入表示的方式。连接器学习让视觉信息在语言任务中更可用；是否还更新视觉塔和语言模型，取决于具体训练配方。

常见思路先利用图文数据建立连接，再用带问题和回答的指令数据学习任务行为。预训练、对齐阶段和指令微调的命名与参数冻结策略因模型而异，不是所有模型都严格经过同样的两阶段流程。

冻结参数只是限制更新对象，模型仍需要执行相应前向计算。若只更新连接器，它的表达能力和训练数据决定能弥补多少接口差异；若解冻更多模块，资源需求与原有能力变化也要重新评估。LoRA 通过训练低秩适配参数调整模型，仍需使用正确标注的数据。

## 9.5 SFT 在哪些位置教模型回答

一条监督样本包含图片、用户问题和人工或其他流程提供的目标回答。训练通常在目标回答的有效文本位置计算下一 token 损失，用真实回答前缀作为条件；用户消息和图像位置提供上下文，通常不计入答案损失；padding 通常通过 attention mask 排除，并在 labels 中标为忽略位置。

例如目标是“12.00”，真实 tokenizer 可能把它分成多个 token。损失在这些目标 token 及按模板约定的结束位置上定义，不能假设整个金额永远是一个 token。视觉占位展开后的位置也需要正确对齐，否则可能错误监督用户问题或漏掉答案。

格式检查可以确认 JSONL 字段存在、角色次序合理、图片路径可读；它不能确认图中真的写着 12.00。把纯色占位图配上详细票据答案，会教给模型没有视觉证据的关联。第四章进一步解释[数据与监督目标](../chapter4/第四章%20数据、训练与微调.md)。

## 9.6 推理阶段不会拿标准答案来更新权重

通常的推理加载已有权重，处理图片与问题，逐步生成回答，不执行优化器更新。图片 token、问题 token 和生成长度共同影响计算成本；KV cache 又带来随已处理位置增长的存储需求。

输出长度限制控制作答空间，采样参数影响候选选择。图像清晰度则由原图和预处理决定。模板不匹配、图像预处理错误、视觉位置丢失和模型能力不足，都可能产生看似流畅的错误回答。

API 路线把模型托管在服务侧，本地路线自行运行 processor 和模型。两者都需要检查是否支持当前图文请求格式；成功返回 HTTP 响应、产生非空文字、答对问题，是三个不同层次的验收。

## 9.7 从一次成功回答到可解释的评估

一张票据回答正确，不足以说明模型普遍会看票据。可能的替代原因包括问题模板泄露答案、背景与金额相关，或训练中见过同源图片。评估应使用独立来源的样本，明确任务评分规则，并记录失败案例。

可以围绕同一任务观察图片质量、问题写法和来源变化如何影响表现；结论必须限定在实际样本与协议上。检查结构化金额是否正确，与评价开放描述是否充分，需要不同评分方式。若模型在看不到必要证据时仍给出确定答案，也应纳入能力边界分析。

# 第八章 构建一个图像问答 Demo


本章用 Gradio 为上一章的图文请求增加交互界面，完成图片上传、问题输入和结果展示。

**衔接**：请求体字段尽量与 [第五章](../chapter5/第五章%20评测体系与工程选型.md) 的 `eval_vlm_dataset.py` 习惯一致（同模型、同 `messages` 结构），这样 Demo 里复现的 bug 能直接回到评测集对照。复杂 OCR / 长图可在 Demo 稳定后翻 [扩展阅读](../扩展阅读.md)。

## 一、检查输入与输出

通过 Demo，可以观察以下四项：

1. 模型接口是否稳定
2. 图像输入链路是否正确
3. 用户问题与输出格式是否合理
4. 输出是否满足所选任务的要求

若出现答错或响应缓慢，先记录输入、配置和返回结果，再按第五、六章的方法定位问题。

本章实现上传、调用和展示。请求失败时会显示异常；第六章讨论的服务级超时、重试和日志系统尚需在应用层实现。

## 二、本章代码说明

配套代码位于：

- `docs/chapter8/code/app.py`
- `docs/chapter8/code/requirements.txt`
- `docs/chapter8/code/.env.example`

这个 Demo 的思路是：

- 前端用 `Gradio`
- 后端通过 OpenAI 兼容接口请求多模态模型
- 用户上传图片并输入问题
- 返回模型答案
- 支持切换多种基础任务模式

## 三、安装依赖

```bash
pip install -r docs/chapter8/code/requirements.txt
```

## 四、配置环境变量

配置可以参考 `.env.example`（`KEY=value` 行格式各系统相同）。若你**不用 `.env`**、而在终端里临时注入变量：Windows PowerShell 用 `$env:KEY="value"`（cmd 用 `set KEY=value`），Linux / macOS 用 `export KEY=value`，详见[基础篇 00](../foundation/00-环境命令行与Python项目基础.md)。

```bash
OPENAI_BASE_URL=http://127.0.0.1:8000/v1
OPENAI_API_KEY=EMPTY
MODEL_ID=your-vlm
GRADIO_SERVER_NAME=127.0.0.1
GRADIO_SERVER_PORT=7860
DEFAULT_MODE=自由问答
```

`GRADIO_SERVER_PORT` 未设置或空白时使用 7860，其他值必须在 1～65535；`DEFAULT_MODE` 未设置或空白时使用“自由问答”，其他值必须是四种已有模式之一。非法配置会在启动页面前报错。

## 五、运行 Demo

```bash
python docs/chapter8/code/app.py
```

运行后会启动本地页面：**页眉会显示当前 `OPENAI_BASE_URL` 与 `MODEL_ID`**，终端里也会打印同一行，改 `.env` 后记得重启进程。上传图片并输入问题即可，例如：

- 请描述这张图的主要内容
- 这张截图里报了什么错误
- 请提取图片中的关键信息
- 请用三点总结这张图的核心内容

这一版 Demo 额外支持四种基础模式：

- 自由问答
- 截图报错分析
- 关键信息提取
- 商品图卖点总结

页面里还会显示一个简单的运行状态，便于你区分：

- 未上传图片
- 正常完成
- 接口调用失败

## 六、请求处理流程

### 1. 上传图片

前端把图片路径传给后端。

### 2. 图片转 data URL

后端把图片编码为 base64，这样能通过标准 OpenAI 兼容消息格式发送。

### 3. 发送图文请求

消息结构通常是：

- 一段文本问题
- 一张图片

### 4. 返回结果

界面展示模型生成的答案。

## 七、从现有模板到结构化字段抽取

第五节的四种模式共用同一条请求链路，区别在于 `TASK_PROMPTS` 中的提示词。当前版本已经显示请求状态和耗时，但没有多图输入、多轮历史、结果持久化或 JSON 校验。扩展前先确定任务需要哪一项能力。

以票据字段抽取为例，现有“关键信息提取”返回条目文本。如果下一步需要程序读取金额，就应先明确输出约定，再增加解析与校验，而不只是多加一个模式名称。

### 1. 明确字段与缺失值

约定输出 `date`、`total` 和 `currency`：日期与金额保留图片中可读的字符串，无法辨认或未出现的字段返回 `null`。下面只是格式示意，不是模型实测结果：

```json
{"date": "2026-05-20", "total": "12.00", "currency": null}
```

提示词应说明字段含义和缺失时的返回方式。不要为了填满字段而要求模型猜测；本例也不把图中日期字符串直接转换成已验证的标准日期。

### 2. 在回答之后校验

现有 `ask_vlm()` 只检查回答是否为非空文本。结构化扩展还需要解析 JSON，检查字段集合和值类型，并把格式错误与接口调用失败分别显示。提示词要求 JSON，不代表返回值一定符合约定。

格式通过之后，还要对照原图检查值是否正确；`total` 是字符串且可解析，并不能证明它对应票据的总金额。需要 OCR、位置或金额规则时，再参考 [Extra01 OCR 与文档理解专题](../Extra-Chapter/Extra01-OCR与文档理解专题.md)。以上解析与校验属于扩展设计，当前代码尚未实现。

### 3. 留下能复查的结果

比较修改前后的模板时，使用相同的图片和问题，并记录模板版本、模型与生成参数、原始回答、解析结果和失败原因。现有页面显示的耗时和状态可供观察，但不会自动形成这些持久记录。

这样，第五章的失败样本能用于检查这次扩展是否改善了字段抽取；第六章的服务记录则帮助区分模型回答错误与请求链路故障。多图和多轮历史可在任务确有需要时另行扩展，不必同时加入。

## 八、章末练习

本节练习任务模板与结构化输出，并检查界面请求和第五章评测脚本是否使用相同配置。

### 必做（约 20 分钟）

1. 为 Demo 新增一种任务模式，并设计对应提示词模板。

### 进阶（约 40 分钟）

1. 阅读 `ask_vlm()`，说明已有耗时显示统计了哪段过程，以及未上传图片、成功返回、调用异常分别走哪条分支。
2. 按第七节的字段约定，让 Demo 返回 JSON，并增加解析和字段类型检查。

### 挑战（1～2 小时）

1. 选择一个场景，把 Demo 改成更像产品的原型（含最少一条用户可见的“失败时该怎么做”提示）。

## 九、本章小结

本章把上传、编码、图文请求和结果展示连接起来，并区分了现有模板与结构化校验扩展。界面能够返回答案后，仍需用评测样本检查内容，并保留失败信息供排查。

需要把问答拆成多个步骤时，继续阅读**第九章**的感知摘要与工具工作流；先核对第七章接口配置，再观察每一步的输入、输出与失败分支。

## 深入学习：先查工程接口

本章侧重应用集成。模型原理与原始论文见 [第七章](../chapter7/第七章%20动手跑通你的第一个%20VLM.md)。

- **Gradio 官方文档**：[Image 组件](https://gradio.app/docs/gradio/image)。重点核对图片值的类型、上传格式与事件回调；按项目实际安装版本查阅。
- **模型接口官方文档**：[图像输入指南](https://developers.openai.com/api/docs/guides/images-vision)。对照图片 URL/base64 格式；OpenAI 兼容服务的限制仍需查服务端自身文档。
- **练习**：在界面与第五章脚本中提交同一张图、同一问题，记录预处理和返回差异，并对照原图核查答案。
